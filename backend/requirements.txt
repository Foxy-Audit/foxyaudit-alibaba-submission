# PDF passport renderer — lazy-imported and NOT installed in the CI/test venv, so
# it's bounded (minor-pinned) rather than exact-pinned since it's unverified here.
#
# ⚠ pip-audit reports PYSEC-2026-2034 against 63.1 (fixed in 68.0): urllib follows
# a redirect without re-running a CUSTOM url_fetcher, so an SSRF allowlist can be
# bypassed on the second hop. Triaged 2026-08-30 (#262). NOT APPLICABLE here —
# routers/passport.py now installs `_passport_url_fetcher`, which accepts ONLY
# `data:` URIs. urllib resolves those in-process, so there is never a first hop
# to be redirected off. Every other scheme raises before `urlopen` is reached.
#

# would have distracted from: the default fetcher was in use with no allowlist at

# choose the URL. Fixed, with the evidence, in tests/integration/
# test_passport_css_injection.py — read that before touching either guard.
#

# Fernet envelope for customer-supplied (BYOK) provider API keys — app/crypto_secrets.py.
#
# ⚠ pip-audit reports PYSEC-2026-36 against 46.0.1 (fixed in 46.0.7): a buffer
# overflow when a NON-CONTIGUOUS buffer reaches `Hash.update()`. Triaged
# 2026-08-30 (#262). NOT REACHABLE — the trigger needs a caller that hands a
# memoryview slice or a reversed buffer to a cryptography primitive, and nothing
# does. Four things were checked, so this need not be re-derived:
#
#   1. `crypto_secrets.py` is the ONLY cryptography call site in the repo
#      (Fernet/MultiFernet). Both directions pass a fresh contiguous `bytes`:
#      `envelope.encode("utf-8")` on encrypt, `str(token).encode("utf-8")` on
#      decrypt.
#   2. The chain does NOT hash with this library at all. `chain.py`,
#      `sdk/hashing.py` and `verifier/foxy_verify.py` all use stdlib
#      `hashlib`/`hmac`, always on `<str>.encode("utf-8")`.
#   3. No `memoryview`, `[::-1]` or `.getbuffer()` exists anywhere in
#      `backend/app`, `sdk/src` or `verifier`.
#   4. Across the whole installed dependency tree, the only `hashes.Hash(…)
#      .update(…)` outside cryptography itself is google-auth's
#      `transport/_custom_tls_signer._compute_sha256_digest`, which feeds
#      `ctypes.string_at(...)` — contiguous — and is only reached on the Google
#      mTLS client-certificate path this deployment never configures.
#
# Fernet's own internals were read at 46.0.1 for completeness: `HMAC.update`, on
# concatenated bytes and on `data[:-32]` (a bytes slice, i.e. a new contiguous
# object). Not `Hash`, and never non-contiguous.
#
# Left at 46.0.1 rather than bumped to 46.0.7: nothing reachable is fixed by the
# bump, and this pin is load-bearing for the KEK envelope.
cryptography==46.0.1
